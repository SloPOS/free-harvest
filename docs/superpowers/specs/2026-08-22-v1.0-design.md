# Free Harvest 1.0 — design

**Status:** partly shipped in 1.0.0 on 2026-08-24

**What actually shipped:** the batch logbook and the control PIN. Alerts and the
learning estimator are specified below but deferred to 1.1 - the estimator
because it cannot honestly be validated without a body of real batches, which
the logbook has only just started collecting, and alerts because they are worth
building on top of a boundary detector that has been exercised by real runs
rather than only by a simulator.

Recording that here rather than quietly editing the plan to match what got
done.
**Companion:** [batch logbook](2026-08-22-batch-logbook-design.md) has its own spec

## What 1.0 means

The project can already monitor a dryer and drive it. 1.0 is the point at which
it also **remembers**, **warns**, and is **safe to put on someone else's
network**.

Four features, in dependency order. Each is small; the ordering exists because
each genuinely needs the one before it.

| # | feature | needs | spec |
|---|---|---|---|
| 1 | Batch logbook | — | [separate](2026-08-22-batch-logbook-design.md) |
| 2 | Control PIN | — | below |
| 3 | Alerts over MQTT | batch boundary detection from #1 | below |
| 4 | Learning time estimator | history from #1 | below |

## Constraints

Measured, not assumed: 731 KB free app flash, 3 MB SPIFFS shared with the
capture log, **24 KB NVS**, and **no PSRAM** — 512 KB SRAM with WiFi, lwIP,
httpd and TinyUSB already resident.

The binding one is RAM. Every feature here computes incrementally and writes
once; nothing accumulates a series in memory. A second TLS client would cost
~40 KB of heap, which is why alerts reuse the MQTT connection that is already
open rather than introducing an HTTPS notifier.

## 2. Control PIN

### Why

The adapter was read-only when the decision was made that network security was
sufficient. It can now start and end 24-hour cycles, and anyone who can reach
the LAN can `POST /api/control`. 1.0 puts this on other people's networks,
including ones with guests, kids, and IoT gear of unknown character.

### Design

A single PIN, 4–8 digits, stored in NVS. **Monitoring stays completely open** —
no login wall, no session for reading state. The PIN gates only the endpoints
that can change the machine:

- `POST /api/control`
- `POST /api/recipes/send`, `/apply`
- `POST /api/cmd`
- `POST /api/ota`

Requests carry `pin=<digits>` alongside their existing fields. Wrong or absent
PIN returns 401 with a reason, exactly as the other refusals do.

The browser keeps the PIN in `sessionStorage` and attaches it automatically, so
it is typed once per browser session rather than per action. A wrong PIN clears
it and re-prompts.

**Not a login system.** No accounts, no cookies, no session tokens. The threat
model is "someone else on the network taps Start", not a determined attacker —
and the honest framing is that this raises the bar rather than making the device
secure. It is stated that way in the UI too.

Rate limiting: after 5 wrong attempts, control endpoints refuse for 60 seconds.
Cheap, and turns an online guess of a 4-digit PIN from seconds into days.

**Off by default is wrong here.** Unlike remote control, the PIN protects rather
than enables, so a fresh device with control enabled and no PIN set shows a
persistent prompt in the UI until a PIN is chosen or explicitly dismissed.

### Testing

Host tests for the PIN check itself (constant-time compare, length validation,
lockout counter). Device tests: every gated endpoint refuses without a PIN and
accepts with one; monitoring endpoints are unaffected.

## 3. Alerts over MQTT

### Why

A batch finishing at 3 a.m. is only useful if something says so. The MQTT
connection is already open and Home Assistant already handles delivery, so this
costs almost nothing.

### Design

Publish to `freeharvest/<id>/event` as retained JSON when:

| event | condition |
|---|---|
| `batch_started` | batch boundary detected (from the logbook tracker) |
| `batch_complete` | phase reaches Complete |
| `batch_interrupted` | run ended early or died mid-cycle |
| `vacuum_stalled` | drying, vacuum above 1000 µm for 15 minutes |
| `link_lost` | no dryer telemetry for 5 minutes |
| `link_restored` | telemetry returns after a loss |

Home Assistant discovery gains a binary sensor and an event entity so
automations can trigger on these without YAML.

**Deliberately not implemented:** an HTTPS notifier such as ntfy. It costs
~40 KB of heap for a TLS session on a device with no PSRAM, to serve users who
have not set up MQTT. If demand appears after 1.0, the right shape is a webhook
POST to a plain-HTTP relay on the LAN, not TLS on the ESP32.

**Thresholds are inference, not measurement.** 1000 µm for 15 minutes is a
guess at what a stalled pull-down looks like; nobody has measured a real vacuum
failure on this machine. They are configurable, and the UI says they are
starting points rather than diagnoses.

### Testing

Host tests for the event state machine: each condition fires once on entry, not
repeatedly; recovery resets it; a flapping link does not emit a storm.

## 4. Learning time estimator

### Why

The current estimate extrapolates linearly while cooling is exponential, so it
under-predicts precisely the slowest final degrees — the ones people are waiting
on.

### Design

Fit Newton's law of cooling to the live trend:

    T(t) = T_ambient + (T_0 - T_ambient) · e^(-kt)

`k` is estimated incrementally from the points already in the trend buffer, so
nothing is stored beyond a handful of accumulator floats. The projected time to
the target temperature comes from the fit rather than from the last slope.

**Learning across batches** uses the logbook: the median `k` from previous runs
of the same recipe seeds the fit, so early in a batch — when there is not enough
curve to fit — the estimate is informed by history instead of being noise. Once
enough points exist, the live fit takes over.

Drying phase duration is not modelled. It is governed by recipe time plus
however much extra drying gets added, which is a setting rather than a physical
process, so the honest estimate is the recipe value and the honest display says
so.

**Confidence must be visible.** An estimator that learns is an estimator that is
sometimes wrong, and a confident wrong number is worse than a hedged one. Show a
range once the fit is poor, and say "estimating" rather than inventing a figure
before there is signal.

### Testing

Host tests: fit recovers a known `k` from synthetic exponential data; noise does
not destabilise it; the estimate converges as points accumulate; a flat series
does not produce an infinite or negative time.

Device verification needs a real batch, so this ships behind the others and is
validated over the following days rather than on the bench.

## Also in 1.0, not features

- **The OTA `panic`.** `reset_reason` reports `panic` after every OTA reboot
  where a clean restart should report `sw`. Harmless in effect — the image boots
  and the filesystem is now unmounted first — but a 1.0 should not crash on
  every update, and the logbook's storage design is partly shaped around not
  trusting that partition.
- **Defrost has never been captured**, and screens 15 and 44 remain
  unidentified. The README should not claim a fully decoded cycle until it is.

## Out of scope for 1.0

Multi-dryer support, any cloud service, a native mobile app, and reading the
dryer's own `.dat` history files — `FILEREAD` answers `A1` to every argument
shape tried so far, and the logbook makes it unnecessary.
